 # Local LLM + Reasoning + Web Search (Mac M-series, MLX)

 This repository provides a lightweight local UI and runtime that combines:

 - a local LLM (MLX-compatible model loader),
 - a zero-training reasoning loop that performs multi-sample reasoning + reflection/verification,
 - optional web search to augment context before answering,
 - a small browser UI with streaming WebSocket responses for a responsive experience.

 This README explains what the project does, how the "thinking" loop is engineered, and how to run the CLI and server. Read carefully for tips on performance and troubleshooting.

 **Repository layout (important files)**
 - `server.py` — FastAPI app exposing `/` (UI), `/ws` (WebSocket streaming), and `/api/chat` (sync endpoint).
 - `static/` — Browser UI (HTML/CSS/JS). The UI talks to the `/ws` endpoint for streaming responses.
 - `reasoning_decoder.py` — Core reasoning orchestration (exposes `reason()`, `GenConfig`, `ReasoningConfig`, and `FINAL_CLOSE_TOKEN`).
 - `run_local.py` — Simple CLI runner that loads your local model and executes a single reasoning request.
 - `download_model.py` — Convenience script to download model files (optional).
 - `model_path.txt` or `MODEL_PATH` env var — Controls which model is loaded.

 **What this project does**
 - Accepts a user question from a browser or CLI.
 - Optionally performs web search (DuckDuckGo/ddgs) and fetches/cleans top results.
 - Builds a compact context from top hits and attaches it to the prompt.
 - Runs a reasoning generation procedure that samples multiple candidate reasoning chains, reflects/verifies, and merges into a final answer.
 - Streams partial text back to the browser over WebSocket for low-latency UX.

 **High-level architecture**
 - Browser UI (`static/index.html` + `static/app.js`) connects to the server via WebSocket `/ws`.
 - Server (`server.py`) optionally runs a search pipeline, then invokes the local model through the reasoning module in a separate thread (non-blocking to the event loop).
 - The reasoning module (`reasoning_decoder.py`) controls sampling and the reflection/verification logic and returns a final string.
 - Server streams incremental deltas back to the client to mimic real-time generation.

 **The Thinking / Reasoning Loop (engineered details)**
 This project implements a practical, zero-shot reasoning pattern that improves answer reliability by combining multiple sampled chains with an internal reflection step.

 1. Search & Fetch (optional)
	 - If `use_web` is enabled and `ddgs` / a search module is available, the server performs a search for the query and fetches the top results.
	 - `trafilatura` extracts usable text from each URL; the server keeps short snippets and builds a compact context limited by `build_context()`.

 2. Prompt Augmentation
	 - The raw user question is wrapped with an instruction prefix and the compact web context via `augment_question()`. This instructs the model to prefer context when available and to cite sources.

 3. Multi-sample Reasoning
	 - The reasoning routine samples `k` independent reasoning chains (default `k=3`). Each chain is generated by sampling from the model with a `GenConfig` (temperature, top-p, max tokens).
	 - Sampling multiple chains reduces the chance of a single sampling path missing the correct logic; it gives the system alternative candidate answers.

 4. Reflect & Verify
	 - After sampling, the routine invokes a reflection/verification step (controlled by `ReasoningConfig.reflect`) that either asks the model to re-evaluate candidate chains or to run a verification step against the provided context.
	 - Reflection can: (a) detect contradictions, (b) synthesize a consensus answer, or (c) fall back to "I don't know" when the context doesn't support confident answers.

 5. Final Compose
	 - The best/consensus output is passed through a final deterministic generation with a `stop` token (see `FINAL_CLOSE_TOKEN`) to produce a clean answer.
	 - The server then returns the answer and the list of sources (if any) to the client.

 6. Streaming UX
	 - For responsiveness, the server chunks the final answer into fixed-size slices and sends them as `{"type":"answer","delta":"..."}` messages over the WebSocket; the client appends these deltas to show text progressively.

 Why this helps: multiple samples + reflection is a lightweight, zero-training alternative to full fine-tuning or chain-of-thought supervision. It reduces brittle single-pass failures by giving the model multiple chances to reason and then encouraging it to self-check.

 **Key types / knobs you should know about**
 - `GenConfig(max_new_tokens, temperature, top_p, stop)` — Controls sampling behavior for generation.
 - `ReasoningConfig(k, reflect)` — Controls how many sampled chains and whether to run reflection.
 - `k` — Number of sampled reasoning chains (higher = more compute but often better reliability).
 - `temperature` & `top_p` — Sampling randomness; lower values make answers more deterministic.
 - `max_new_tokens` — Controls response length and cost.


 Running locally — quick start
 -----------------------------
 Prerequisites:
 - Apple Silicon (recommended) or a system compatible with MLX model loader.
 - Conda/Miniforge environment as provided by `environment.yml` (recommended).

 1) Create the environment (recommended):

 ```bash
 conda env create -f environment.yml
 conda activate r78m-web-reason
 python -m pip install -U pip
 ```

 2) (Optional) Download or point to a model:
 - Either set `MODEL_PATH` env var to a HuggingFace-style ID or a local folder path, or place the path in `model_path.txt`.
 - Alternatively run `python download_model.py` to download a default model (if that script is configured for your desired model).

 3) Run the server (browser UI)

 ```bash
 # Use the Python from the environment you created
 python -m uvicorn server:app --host 127.0.0.1 --port 8000
 ```

 Then open `http://127.0.0.1:8000` in your browser. The UI will connect to `/ws` to stream responses.

 4) Run a CLI query without the web UI

 ```bash
 # Loads local model and runs a single reasoning request
 python run_local.py "Explain binary search in one sentence."
 ```

 5) Non-streaming API (for quick tests)

 ```bash
 # Example using curl against the sync endpoint
 curl -X POST "http://127.0.0.1:8000/api/chat" -H "Content-Type: application/json" \
	-d '{"message":"Who won the 2024 US presidential election?","use_web":true}'
 ```

 Security & networking notes
 - By default the server binds to `127.0.0.1` (local-only). To expose externally, run `--host 0.0.0.0` and ensure you understand firewall and security implications.
 - The code can optionally perform web search; if you run in sensitive/offline environments, disable web search and/or remove search credentials.

 Performance & memory tips
 - Use 4-bit / quantized models where possible to fit on Apple M1/M2/M4 memory.
 - If you run out of memory, reduce `max_new_tokens` and/or choose a smaller model.
 - Lower `k` reduces CPU/latency cost proportionally.

 Troubleshooting
 - "No local model path found": create `model_path.txt` or set `MODEL_PATH` env var to a valid model path.
 - "python: command not found" when starting `uvicorn`: run the Python that belongs to your Conda environment (example above shows how to use that interpreter directly).
 - Search not working: the repo tries `ddgs` then `duckduckgo_search`; if neither is installed, web search is effectively disabled. Install one of them if you want web search.
 - Web UI send button not responding: ensure the browser console has no JS errors and that `/ws` is reachable; server logs (uvicorn) show accept/connect events when the UI connects.

 Advanced: How to reason about modifying the loop
 - The core procedure lives in `reasoning_decoder.py`. To experiment:
	- Change `k` to increase/decrease alternative chain sampling.
	- Toggle `reflect` to disable the verification step if you want purely sampled outputs.
	- Change `GenConfig` parameters to favor conservative or creative answers.

## Notes
- Default model is `meta-llama/Llama-3.2-1B-Instruct`. You can switch to `Qwen/Qwen2.5-1.5B-Instruct`.
- The reasoning loop needs **no training**. Fine-tuning (LoRA) is optional later.
- `ddgs` search requires no API key. For production, consider a dedicated search API.
